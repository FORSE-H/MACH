# How MACH scores entries

Every entry in MACH carries a judgement — **Adopt**, **Assess**, or **Caution** — and a plain-English reason explaining it. This page documents how those judgements are produced.

---

## The short version

Judgements are computed algorithmically from verified signals (GitHub stars, license, registry downloads, published papers). No LLM writes them. Every claim in a `judgementReason` traces back to a source API call.

---

## Two scores per entry

| Score | What it measures | Max |
|---|---|---|
| **Editorial score** | Community traction, governance, evidence quality, licence | 16 pts |
| **FAIR score** | Findability, Accessibility, Interoperability, Reusability | 8 pts |

### Editorial score → Adopt / Assess / Caution

Signals vary by entry type — applying software signals (GitHub stars, registry downloads) to a government data API or a standards specification produces meaningless scores. Each category uses its own signal set. Signals that don't apply to a category are excluded from both the score and the denominator.

**Common to all categories:**

| Signal | What we check | Points |
|---|---|---|
| Governance | foundation or community / academic or government / vendor-led / individual | 0 – 3 |
| Licence | permissive / copyleft / none | 0 – 2 |
| Evidence count | ≥ 2 evidence items | 0 – 1 |

**software · mcp-servers** additionally score: maturity, forks, stars, registry downloads (PyPI/conda/npm/CRAN/Maven/Docker/HuggingFace), evidence quality (peer-reviewed paper).

**ai-ml-models** score the same signals as software, plus weights licence (scored separately from code licence) and EU AI Act risk class. The risk class does not reduce the raw score — instead it sets a ceiling on the achievable ring: a high-risk model is capped at Assess unless a peer-reviewed clinical validation paper exists in the evidence list. With that paper the cap is lifted and Adopt is possible. Risk class is assigned by the curator at triage against [EU AI Act Annex III](https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=CELEX:32024R1689#anx_III), aided by an automated keyword scan of the `intendedUse` field.

**data-sources** (e.g. ClinicalTrials.gov, PAHO OpenData) score: operational status (live/degraded/offline), update frequency, whether a structured API exists, documentation quality, geographic coverage.

**specs** (e.g. CDISC ADaM, FHIR R4) score: spec status (stable/draft/deprecated), adoption breadth (how many catalog entries implement it), regulatory endorsement (FDA/EMA/CMS/NHS), revision history.

**datasets** score: access model (open/registration/DUA/proprietary), download counts (HuggingFace/Zenodo/Figshare/PhysioNet), citation count (OpenAlex), evidence quality.

**catalogs** (e.g. FAIRsharing, bio.tools, OpenAIRE) score: number of entries held, update frequency, whether a machine-readable API exists, curation model (editorial/community/automated), interoperability with DCAT or schema.org standards.

**Threshold:** score is normalised to the applicable signals for that category. ≥ 60% → Adopt · 35–59% → Assess · < 35% → Caution.

### FAIR score

Based on [FAIRsoft indicators](https://doi.org/10.1371/journal.pcbi.1007854):

| Indicator | What we check |
|---|---|
| F1 | Unique identifier present and resolvable |
| F2 | Listed in a community registry (PyPI / conda / npm / CRAN / Maven / HF / Docker) |
| A1 | Code repository resolves (HTTP 200) |
| A2 | Version or date recorded |
| I1 | Open health standard referenced (FHIR / OMOP / SNOMED / DICOM / openEHR / HL7) |
| I2 | OSI-approved SPDX licence identifier present |
| R1 | Citable: SWHID or CITATION.cff present |
| R2 | Governance: CONTRIBUTING.md, GOVERNANCE.md, or ≥ 2 evidence items |

**Thresholds:** ≥ 6 → Good · 4–5 → Partial · < 4 → Insufficient

## Where the judgementReason comes from

The `mach:judgementReason` field on every entry is generated from the score breakdown — not written by hand and not generated by an AI. Every sentence traces to a verified API signal:

- Star and fork counts → GitHub API
- Licence → GitHub SPDX field
- Registry downloads → PyPI / conda / npm / CRAN / Maven / Docker / HuggingFace APIs
- Paper verified → arXiv or DOI resolution (HTTP 200 + metadata check)
- Last commit / last release → GitHub API

The "why this ring and not the one above" explanation is also computed: if an entry scored 8/16 instead of 9/16, the reason names the specific missing signal.

---

## How often scores are refreshed

Signals are re-harvested weekly by CI. If signals change (detected by hash comparison), a new score is computed and the entry's `mach:editorialReviewedAt` date is updated. If nothing changed, only the internal "last checked" timestamp is updated — no unnecessary writes.

---

## Overrides

The algorithm suggests a judgement. The maintainer approves it via GitHub PR review. In rare cases where the algorithm misses context (a project is archived, a safety concern exists), an override can be set in `overrides.yaml` with a documented reason. Overrides are visible in the Git history.

## Questions or disagreements

If you think an entry is rated incorrectly, open a GitHub Issue labelled `appeal` with your evidence. See [GOVERNANCE.md](GOVERNANCE.md) for the appeal process.
